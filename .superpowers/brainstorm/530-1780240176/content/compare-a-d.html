Comparativa: Feature Request Board vs Knowledge Base

Análisis detallado de complejidad, entidades y arquitectura

Opción A: Feature Request Board
Concepto: Un portal donde los usuarios proponen features, votan, y el equipo gestiona el roadmap.

Entidades principales

  • User — registro, roles (user/admin)
  • Board/Project — agrupa requests por producto
  • FeatureRequest — título, descripción, estado, autor
  • Vote — un voto por usuario por request
  • Comment — discusión en cada request
  • Status — planned, in progress, shipped, declined

Features clave

  • Auth con JWT (registro, login, roles)
  • Crear/votar/comentar requests
  • Kanban board con drag & drop (admin)
  • Filtros por estado, popularidad, fecha
  • Changelog público de lo implementado

Opción D: Knowledge Base
Concepto: Espacio personal/equipo de notas interconectadas con editor Markdown y visualización de grafos.

Entidades principales

  • User — registro, perfil
  • Workspace — espacio de trabajo (personal/equipo)
  • Note — contenido Markdown, título, metadata
  • Tag — etiquetas para organizar
  • Link — conexiones entre notas (backlinks)
  • Collection — agrupación jerárquica de notas

Features clave

  • Editor Markdown WYSIWYG
  • Graph view de conexiones entre notas
  • Búsqueda full-text (PostgreSQL tsvector)
  • Sistema de tags y colecciones anidadas
  • Auto-backlinks al mencionar [[otra-nota]]

¿Cuál demuestra mejor la arquitectura?

A: Feature Request Board

Pros para la prueba

  • Más endpoints = mejor demostración de capas
  • Lógica de negocio clara (votos no duplicados, estados)
  • Drag & drop = interacción frontend avanzada
  • Roles admin/user = autorización real
  • Flujo completo: idea → voto → roadmap → shipped

Contras

  • Kanban requiere más tiempo de frontend
  • Menos "visualmente impresionante" que un grafo
D: Knowledge Base

Pros para la prueba

  • Graph view = impacto visual muy alto
  • Editor Markdown = componente frontend rico
  • Full-text search = feature de infraestructura interesante
  • Backlinks [[ ]] = lógica de parsing no trivial

Contras

  • El graph view es complejo de implementar bien (D3.js)
  • Menos entidades de negocio ≠ menos demostración de arquitectura
  • Editor WYSIWYG puede desviar el foco del backend
Mi recomendación

Opción A (Feature Request Board) es mejor para esta prueba de arquitectura porque:

  1. Más entidades de dominio → la clean architecture se luce más
  2. Autorización por roles → middleware, guards, permisos
  3. Lógica de negocio real → validar votos duplicados, transiciones de estado
  4. Kanban board → operaciones PATCH masivas al reordenar (drag & drop)
  5. Balanceado — complejo pero no abrumador. Se puede entregar completo.

Si lo visual es prioridad, la Opción D gana con el graph view, pero el esfuerzo en D3.js puede restar tiempo a demostrar la arquitectura del backend.
